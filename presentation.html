03. Risk Prioritization

Material vs. Generic Risk

I am intentionally ignoring generic model drift. The material risks in Compass are systemic, silent failures at the data infrastructure layer.

🚨

1. Training/Serving Skew

The formula divergence (Exact vs EWMA) breaks the fundamental assumption of machine learning. The model is miscalibrated in production by design.

⚠️

2. Silent Staleness

FRESHNESS_TTL = 6h is defined in config but never enforced in online_store.py. The API serves infinitely stale features while the dashboard happily reports 100% uptime.

04. Trade-off Reasoning

Position on Proposed Changes

PAUSE
Change 1: Real-time top-ups

Reasoning: Automating financial decisions on top of mathematically skewed and silently stale data creates unacceptable regulatory and financial exposure.

Path to unlock: Enforce TTL at read-time and unify the formula logic before proceeding.

PROCEED
Change 2: Lighter feature review

Reasoning: Human review is a bottleneck, not a guarantee of safety. We can ship faster and govern better by replacing manual checks with automated parity gates.

Condition: Hard CI gate that blocks merge if Offline vs Online PSI > 0.10.

05. Framework Thinking at Scale

Governing a Data Mesh

You cannot force identical engineering maturity across all domains. Governance must focus on interoperability, not implementation.

Principle: Standardize the Contract, not the Code

  • Org-Wide Mandates (The Contract): Every feature must have a registered schema, a freshness SLA, and pass the automated Parity/PSI gate in CI.
  • Domain Autonomy (The Implementation): Teams choose their compute engine (Spark, Flink, dbt) and window strategies, as long as the contract is met.
  • Adoption Incentive: Provide a "Paved Road SDK" that includes out-of-the-box parity tests and monitoring. Compliance must be easier than non-compliance.
