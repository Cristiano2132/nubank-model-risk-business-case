02 Risk Landscape

What I found running the system

Risk 1 — Training/Serving Skew

The pipeline is mathematically inconsistent. The exact same feature txn_amount_avg_30d is computed differently depending on the serving path.

Evidence: The Skew Distribution

Impact
Mean offline/online delta is 29.5%.

Consequence
70% of customers have >15% divergence.

Risk 2 — Silent Staleness

The TTL is a dead config. FRESHNESS_TTL is defined in config.yaml but is never imported or checked during OnlineStore.get_features().

Evidence: Feature Age Distribution

All 300 customers have features older than the 6-hour SLA. The pipeline is serving stale data without warning.

03 Assessment Approach

How I validate the system

Testing the Live System

  1. Parity Check: Query C0001 from both stores. If offline ≠ online, pause.
  2. Staleness Check: Query online store metadata. If age > TTL without fallback, pause.
  3. Data Quality Check: Assert nulls, schemas, and boundaries on transactions.csv.
  4. Deployment Safety: Look for feature versioning. (None exists).
  5. Monitoring Scope: Check dashboard.py. (Only tracks API uptime, not data health).

04 Position on Changes

Verdict on Proposed Changes

🔴 PAUSE: Switch to streaming for Underwriting
You cannot train on exact means and serve on EWMA without a major credit policy violation.

🟡 PROCEED WITH CONDITIONS: Self-serve ML
We can scale the platform, but only if we codify Governance into the SDK.

05 Data Mesh

Scaling safely

The Paved Road SDK

Standardize the Contract, not the Implementation.

  1. Enforced Schemas: Cannot push to registry without defined schema.
  2. Baked-in Quality: SDK wraps write_features with Great Expectations.
  3. Mandatory Monitoring: SDK emits PSI and freshness metrics automatically.

Summary

The tension isn’t between shipping fast and governing well. It’s about recognizing that in infrastructure, unvalidated speed is tech debt. We must build safety directly into the golden path.
