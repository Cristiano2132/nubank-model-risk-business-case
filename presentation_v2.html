What is Compass?

Batch: Nightly full recompute. Exact arithmetic mean over 30-day window.

Streaming: Incremental per event. EWMA α=0.2 — a recency-biased exponential smoother.

Monitoring: API uptime & latency only. No data quality checks whatsoever.

Context · Batch Path

Batch Pipeline — Exact 30-day Mean

flowchart LR A["transactions.csv"] -->|read_csv| B["DataFrame\n(all 32,929 rows)"] B -->|"filter: last 30d\nfrom as_of"| C["Windowed DataFrame\nper customer"] C -->|"groupby customer_id\n.mean()"| D["Dict: customer_id to avg"] D -->|for each customer| E["OfflineStore\n.write_features()"] E -->|"INSERT OR REPLACE"| F[("offline_store.db\nPK: customer_id, as_of, feature_name")]

✅ Strengths

  • Exact arithmetic mean — reproducible and precise
  • Point-in-time safe (keyed by as_of, preserves history)
  • The source of truth used for model training

❌ Limitations

  • Expensive: full table scan on every run
  • Nightly cadence → hours-old data at serving time
  • Cannot support real-time credit decisions — hence streaming was built

Context · Streaming Path

Streaming Pipeline — EWMA Smoother

flowchart LR A["transactions.csv"] -->|sort by timestamp| B["Ordered Events\nwith seq index"] B -->|"resume from\nlast_processed_seq"| C["Pending Events\nstart_seq onwards"] C -->|batches of 50| D{"customer_id\nin running_avg?"} D -->|Yes| E["EWMA Update\n0.2 × amount + 0.8 × prev"] D -->|No| F["Seed\nrunning_avg = amount"] E --> G["OnlineStore\n.upsert_feature()"] F --> G G -->|"UPDATE value, computed_at"| H[("online_store.db\nPK: customer_id, feature_name")] G -->|UPDATE| I[("pipeline_state\nlast_processed_seq")]

✅ Strengths

  • Fast: O(1) per event, no full table scan
  • Incremental: resumes from last position via pipeline_state

❌ Critical Issues

  • Approximate: EWMA ≠ 30d arithmetic mean
  • Order-sensitive: result changes with event arrival order
  • Silent staleness: FRESHNESS_TTL defined in config, never enforced at read

Assessment — P1 & P2

Parity Tests · Drift Detection

P1 — Offline/Online Parity

Compute every feature via both paths. Compare with KS-test + PSI. Thresholds pre-defined.

Parity Pass Criteria
psi = compute_psi(offline_vals, online_vals) ks_p = ks_2samp(offline, online).pvalue delta = mean(abs(off-on)/off * 100) PASS if: psi < 0.10 and ks_p > 0.05 and delta < 5

Compass: PSI=0.08 (AMBER borderline), p=0.002 → FAIL. 14% decision flip rate.

P2 — Drift Detection

Sliding window PSI vs. 30-day baseline. Thresholds define action — not observation.

RAG Thresholds

GREEN

PSI 0–0.10 → Stable. No action.

AMBER

PSI 0.10–0.25 → Investigate within 24h.

RED

PSI >0.25 → Auto-alert. Block T1 serving.

Compass Risk Assessment · Position on Changes13 / 19
Change 1 — Real-time top-ups, no human review

Position: PAUSE

🛑
PAUSE — Remediation Required First

Automating financial decisions on data that is provably skewed (46% delta) and silently stale creates unacceptable regulatory and credit risk. We cannot govern our way out of a math problem after the fact.

Required Gates to Unlock — Estimated 3–4 Weeks

  • 1
    Reconcile formula divergence — Unify batch and streaming logic. Confirm parity PSI <0.05 over 7-day shadow run before any production traffic.
  • 2
    Enforce TTL at read path — Add freshness check in online_store.get_features(). Alert on breach. Confirm <1% staleness rate in prod.
  • 3
    Deploy feature-quality KRI dashboard — PSI, staleness, parity delta visible and alerting before go-live.
  • 4
    Validate rollback playbook — Fire drill completed. MTTR <15 min confirmed.

Change 2 — Lighter review for feature transformation code

Position: Proceed with Conditions

🟡
PROCEED WITH CONDITIONS

The speed argument is legitimate. Manual reviews are a bottleneck with inconsistent coverage. We can move faster and govern better — by replacing slow human checks with rigorous automated parity gates in CI.

Required Automated Gates

  • 1
    Parity test in CI — Every merge triggers parity suite. <5% delta = hard block.
  • 2
    PSI gate at deploy — Before/after distribution comparison. PSI >0.10 blocks deployment.
  • 3
    Shadow deploy for T1 changes — 7-day parallel run before cutover.
  • 4
    Rollback SLA — Documented and tested. MTTR <15 min.

Expected Outcome

Review cycle: 5–7 days → 1–2 days for most changes, with higher automated test coverage than today's manual process.

Framing for Teams

Frame as acceleration, not governance. The gates are the prerequisite for speed, not the opposite. Teams with GREEN KRIs ship faster.

Governing at Scale — Uneven Team Maturity

🔒

Standardize Org-Wide (The Contract)

  • Feature schema + version registry
  • Freshness SLA tiers (T1 <1h, T2 <6h, T3 <24h)
  • 5 mandatory KRIs with fixed RAG thresholds
  • CI parity gate: hard block on PSI >0.10
  • Lineage: git_sha, run_id on every write
🧩

Leave to Domain Teams (The Implementation)

  • Pipeline tech: Spark, Flink, dbt, pandas
  • Storage technology (within SLA)
  • Window sizes and domain-specific logic
  • Compute scheduling and infra
🛤️

Adoption Without Authority

  • Paved Road SDK — Compliance built-in, not extra work
  • Public KRI dashboard — RED blocks T1 serving
  • Risk Champions embedded — Partners, not auditors

"Standardize the interoperability contract — what the feature output must guarantee. Leave the implementation to the domain team."
